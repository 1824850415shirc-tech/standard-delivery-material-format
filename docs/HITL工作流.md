# HITL 文档生成工作流

本流程只适用于从材料撰写或实质性重写交付文档。用户已经提供完整 Markdown，并且只要求规范格式或直接渲染 DOCX 时，不重复收集材料或确认大纲；应先按 `references/direct-markdown-render.md` 生成规范化 Markdown 副本，再进入统一渲染与校验流程。用户提供已有 DOCX，只要求按标准格式重新排版时同样不走本流程，应按 `references/existing-docx-import.md` 先提取并规范化内容，再进入统一渲染与校验流程。

## 1. 流程目标

本流程将交付文档生成拆成“材料确认—大纲确认—正文生成”三个阶段。用户负责提供事实材料和审批大纲，生成工具负责梳理来源、组织结构和撰写内容。

```text
用户提出文档需求
        ↓
请求并接收已有材料
        ↓
核对材料、冲突和缺口
        ↓
生成带章节简述的大纲
        ↓
用户确认大纲？ ── 否 ──→ 修改大纲并再次确认
        │
        是
        ↓
按确认大纲生成正文
        ↓
结构、来源与隐私检查
```

## 2. 阶段一：材料收集

首次收到“帮我写一份详细设计说明书”等请求时，应先回复：

> 可以。请先提供已有材料，我会先依据材料和内置模板整理一份带章节简述的大纲，等你确认后再写正文。建议优先提供：【按文档类型列出材料】。没有的材料可以直接说明“暂无”。

此阶段应做到：

- 说明建议材料及其用途；
- 接收文件、目录、代码仓库或用户补充的事实描述；
- 不要求用户重复提供已经给出的内容；
- 不开始生成完整正文。

## 3. 阶段二：材料核对与大纲

收到材料后，先给出材料核对结果：

| 材料 | 可支持内容 | 状态 | 备注 |
| --- | --- | --- | --- |
| 【文件名或材料名称】 | 【对应章节】 | 已读取/待补充/存在冲突 | 【说明】 |

然后生成大纲。每个章节只写简述和来源，不展开正文：

```markdown
## 2. 总体设计

简述：说明系统边界、组件关系、主要调用链和关键技术约束。

来源：技术规格说明书、系统架构图
```

缺少依据时使用：

```markdown
## 5. 接口设计

简述：整理接口清单、调用方向、鉴权、超时和错误处理要求。

【待补充：接口清单或接口文档】
```

## 4. 大纲确认卡

每次请求用户确认大纲时，至少包含以下内容：

| 项目 | 内容 |
| --- | --- |
| 文档类型 | 【模板名称】 |
| 大纲版本 | V0.1、V0.2 等 |
| 已使用材料 | 【材料清单】 |
| 主要缺口 | 【待补充项；无则写“无”】 |
| 结构变化 | 【相对上一版的变化；首次写“首次提交”】 |

确认提示统一使用：

> 请确认以上大纲。你可以回复“确认大纲”，也可以指出需要增加、删除、合并或调整的章节。收到明确确认后，我再生成正文。

## 5. 阶段三：正文生成

只有用户明确确认当前大纲后才能开始。正文应：

- 严格沿用已确认的章节结构；
- 以已读取材料和用户确认信息为事实边界；
- 将推测改写为建议、假设或待确认项；
- 保留原始命令、参数、接口名、路径和合同约束；
- 完成结构、来源、占位符和隐私检查后再交付。

如果正文编写过程中发现必须新增或删除一级章节，应暂停正文生成，提交修订后的大纲并再次请求确认。
