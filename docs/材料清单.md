# 各类文档建议材料清单

材料清单用于引导用户提供已有依据，不表示每个项目都必须具备全部文件。缺失材料记录为待补充项，不据此编造内容。

## 一、项目前期

### 1. 项目章程

优先提供：

- 立项申请、任务书、合同、招标文件或会议决议；
- 项目背景、业务目标、范围边界和预期成果；
- 项目干系人、组织分工、决策和汇报机制；
- 预算、计划周期、关键里程碑和资源约束；
- 已知风险、前提假设和成功标准。

### 2. 调研方案

优先提供：

- 调研任务、决策背景和待回答的问题；
- 已有业务、系统、组织和数据范围说明；
- 计划访谈的角色、部门或外部对象；
- 可用资料、统计数据、现场条件和时间窗口；
- 保密、合规、数据使用和成果确认要求。

### 3. 调研报告

优先提供：

- 项目章程、合同、技术规格说明书等已明确项目背景、目标、范围、组织、成功标准或总体计划的前序材料；
- 已确认的调研方案、问题清单、调研范围和执行安排；
- 访谈纪要、问卷、现场记录或会议材料；
- 现状流程、系统清单、统计数据和问题记录；
- 备选方案资料、同类案例和验证结果；
- 适用的制度、标准、预算和时间约束。

编制时先建立前序材料的版本和章节引用关系。已确认且本次未发现变化的内容不在报告中重复改写；报告重点记录实际调研证据、核验结果、变化、冲突、分析和待决策事项。

### 4. 实施方案

优先提供：

- 合同、任务书、项目章程和已确认范围；
- 需求、调研结论、总体设计或技术方案；
- 现有环境、网络、软硬件和资源清单；
- 计划周期、里程碑、人员分工和现场窗口；
- 数据迁移、部署切换、回退、验收和安全要求。

## 二、项目过程

### 1. 需求规格说明书

优先提供：

- 当前有效的 PRD、版本变更记录、Roadmap、User Story 和产品评审结论；
- 与 PRD 配套的业务流程、交互原型、页面截图、状态说明、数据字段和待定问题；
- 合同、招标文件、任务书或项目范围说明；
- 业务流程、调研记录、访谈纪要和现状材料；
- 既有系统说明、数据字典和接口资料；
- 验收要求、合规制度和性能目标；
- 技术可行性、安全、部署和运维评审结论。

PRD 是产品需求的主要来源，但不单独决定项目交付范围。编制时核对 PRD 版本、优先级和评审状态，将其中已确认的产品内容转换为可验证需求。竞品调研、内部技术方案、原型批注和待定项不直接形成交付承诺；需与合同范围、业务确认、技术评审、安全合规和验收标准交叉核验。

### 2. 详细设计说明书

优先提供：

- 已确认的需求规格说明书或技术规格说明书；
- 源代码、代码仓库目录或关键模块代码；
- 总体设计、架构图、部署图和组件说明；
- 数据库设计、数据字典、接口文档和消息定义；
- 运行环境、配置清单、安全规范和验收标准。

### 3. 数据库设计

优先提供：

- 需求规格说明书、详细设计和业务数据模型；
- 现有数据库结构、DDL、数据字典和 ER 图；
- 数据量、增长率、查询场景和性能目标；
- 数据安全、审计、保留、归档和合规要求；
- 备份恢复、迁移、版本发布和回退要求。

### 4. 测试方案与用例

优先提供：

- 已确认的需求、设计、接口和验收标准；
- 测试范围、版本计划、质量目标和缺陷规则；
- 测试环境、账号权限、测试工具和数据条件；
- 历史缺陷、高风险模块和生产问题记录；
- 性能、安全、兼容性等专项测试要求；
- 前序迭代的测试方案、用例、执行记录和测试报告，并标明对应版本、迭代、执行轮次和状态；
- 用例编号规则、需求与用例映射，以及已废止、替代或拆分合并的用例记录。

收到多份迭代材料时，先核对用例编号、被测版本、执行轮次和指标口径。测试报告中的实际结果不反向改写当时的测试计划；复测或回归通过也不删除早期失败记录。存在编号错位、用例数量不一致或判定标准冲突时，列为待确认项。

### 5. 测试报告

优先提供：

- 已确认的测试方案、测试用例和版本基线；
- 用例执行记录、测试日志和测试证据；
- 缺陷清单、修复验证记录和遗留问题；
- 性能、安全、兼容性等专项测试结果；
- 需求覆盖统计、通过口径和测试结论依据。

### 6. 运维手册

优先提供：

- 当前有效的系统版本、部署图、运行环境和主要服务清单；
- 客户运维人员与建设方技术支持的职责分工、支持入口和问题升级方式；
- 启动、停止、健康检查、日常巡检、监控告警和日志查看方法；
- 备份任务、备份结果检查、恢复流程和恢复后的验证方法；
- 常见故障、历史工单、已验证处置方法和客户可执行的操作边界；
- 账号安全、变更升级、运维记录、培训材料和已有运维手册。

历史手册、规格书和设计文档只代表对应版本的记录或要求。服务名称、地址、端口、路径、备份策略、响应时限和操作命令以当前部署记录或现场核验为准；账号、密码、令牌、密钥和未批准的生产信息不得写入交付文档。

### 7. 系统接口文档

优先提供：

- 当前有效的 Apifox 项目导出，以及 OpenAPI/Swagger JSON 或 YAML；
- Apifox 导出的 PDF、HTML 或 Markdown 发布快照，并标明导出时间、版本和范围；
- 系统架构、集成关系、调用方向和网络边界；
- 接口分组/Tag、环境变量、Base URL 占位符、安全方案和认证授权流程；
- 请求响应示例、Schema/Data Model、枚举、数据字典、HTTP 状态码和业务错误码；
- 签名、加密、幂等、限流、超时、重试、消息、回调和文件传输约定；
- 联调记录、版本兼容、监控指标和服务级别要求。

优先使用机器可读的 OpenAPI JSON/YAML 或 Apifox 项目导出检查接口完整性与变更，PDF/HTML/Markdown 作为发布快照和人工复核。Apifox 定义、Mock 示例和自动生成响应不自动证明接口已实现、已部署或已联调；实际状态需以环境、代码、日志和联调证据核验。材料中的真实 Token、密钥、Cookie、个人信息和未批准生产地址不写入交付文档。

### 8. 操作手册

优先提供：

- 当前有效的系统版本、发布日期、适用环境和功能清单；
- 用户角色、权限矩阵、账号开通方式和数据访问范围；
- 菜单结构、业务流程、字段规则、状态流转和操作限制；
- 测试环境页面、脱敏截图、原型或演示材料，并标明对应版本或采集时间；
- 导入导出模板、字段字典、状态说明、错误码和已知问题；
- 已有用户手册、培训材料、验收用例、常见问题和支持升级流程。

已有手册、原型和截图只证明对应版本中的文档或界面状态，不自动证明当前功能已经上线、权限配置已经生效或业务流程未经变更。编制时核对系统版本、发布记录、测试结果和实际授权；图片与附件使用相对路径随 Markdown 一起保存，并清除账号、地址、人员、联系方式及业务数据等敏感信息。

## 三、项目收尾

### 1. 验收报告

优先提供：

- 合同、任务书、需求基线、变更确认和验收标准；
- 项目交付物清单、版本信息和提交记录；
- 测试报告、试运行报告、培训和移交记录；
- 验收用例、检查记录、问题整改和关闭证据；
- 遗留事项、责任分工和后续完成计划。

### 2. 试运行报告

优先提供：

- 试运行方案、上线确认、运行范围和起止时间；
- 实际部署版本、环境配置和变更记录；
- 业务使用量、性能指标、监控和可用性数据；
- 告警、故障、用户反馈和问题处理记录；
- 备份恢复、运维值守、培训移交和改进计划。

## 四、材料处理原则

- 优先使用版本明确、已确认且与当前交付范围一致的材料。
- 分别核对合同约束、技术实现和运行现状，不能相互替代。
- 源代码反映实现，但不自动证明业务验收口径。
- 合同反映约定，但不自动证明系统已经实现。
- 历史文档可能过期，标注版本并与当前材料交叉核对。
